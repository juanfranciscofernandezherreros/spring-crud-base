# explicit-bean-wiring

Turns implicit, scan-discovered beans (`@Service`, `@Component`) into
explicit `@Bean` factory methods in one central `@Configuration` class —
the whole dependency graph readable in one file instead of scattered
annotations. Apply this last, after the rest of the CRUD stack exists,
since it touches every class that currently carries a stereotype
annotation.

## 1. What moves, what stays, and why

| Class kind | Keep on the class | Move to `@Bean` | Why |
|---|---|---|---|
| Service impl (`@Service`) | nothing | the whole thing | plain business logic, no framework requirement |
| Mapper (MapStruct, `@Mapper(componentModel="spring")`) | nothing | the whole thing | drop `componentModel="spring"` entirely so the generated `*Impl` carries no `@Component`; `new` it directly in the `@Bean` method |
| Filter (`@Component` + `@Order`) | `@Order` only | the whole thing | Spring Boot auto-registers any `Filter`-typed bean it finds regardless of how it got there — no stereotype needed at all |
| `@RestController` | `@RestController` (or `@Controller`) **and** the class-level `@RequestMapping` | the instantiation only | Spring MVC's `RequestMappingHandlerMapping.isHandler()` requires this annotation to recognize the class as a handler — that check is independent of *how* the bean was registered |
| `@RestControllerAdvice` | `@RestControllerAdvice` | the instantiation only | same reasoning — it's an MVC-infrastructure marker, not a DI concern |
| Spring Data JPA repository interface | everything, unchanged | **nothing** | the repository isn't a plain class — it's a proxy generated by `JpaRepositoryFactoryBean` via reflection at startup; there is no constructor to call from a `@Bean` method. Forcing this fights the framework for zero benefit. Leave it auto-configured. |

## 2. The central config class

```java
@Configuration
public class BeanConfig {

    @Bean
    public EntityMapper entityMapper() {
        return new EntityMapperImpl(); // MapStruct-generated, no componentModel
    }

    @Bean
    public EntityService entityService(EntityRepository repo, EntityMapper mapper, MeterRegistry meterRegistry) {
        return new EntityServiceImpl(repo, mapper, meterRegistry);
    }

    @Bean
    public EntityController entityController(EntityService service) {
        return new EntityController(service);
    }

    @Bean
    public GlobalExceptionHandler globalExceptionHandler() {
        return new GlobalExceptionHandler();
    }

    @Bean
    public RequestLoggingFilter requestLoggingFilter() {
        return new RequestLoggingFilter();
    }
}
```

Since the impl classes still use `@RequiredArgsConstructor` (or a plain
constructor) for their fields, this is just calling that constructor
explicitly instead of letting component-scanning discover and call it —
the actual dependency graph doesn't change, only how visible/explicit it is.

## 3. Exclude the MVC-annotated classes from component scanning

`@RestController`/`@RestControllerAdvice` are themselves `@Component`
meta-annotations, so leaving them on the class means classpath scanning
*will* auto-register a second instance alongside the one this config class
creates — two beans of the same type, and Spring MVC registers every
mapped route twice, failing to start with an ambiguous-mapping error.
Exclude those specific classes from the scan on the main application class:

```java
@SpringBootApplication
@ComponentScan(excludeFilters = @ComponentScan.Filter(
        type = FilterType.ASSIGNABLE_TYPE,
        classes = { EntityController.class, GlobalExceptionHandler.class }))
public class Application { ... }
```

Plain former-`@Service`/former-`@Component` classes need no such exclusion
— once the stereotype annotation is gone, scanning simply doesn't see them
at all.

## 4. The pitfall that will actually bite: test-slice isolation (confirmed, not hypothetical)

Spring Boot's test slices (`@DataJpaTest`, `@WebMvcTest`, `@JsonTest`, ...)
narrow the context by excluding classes carrying specific stereotypes
(`@Service`, `@Component`, `@Controller`) via `TypeExcludeFilter` — that's
exactly the mechanism this skill removes. A slice test **does not exclude
plain `@Configuration` classes**, so once every bean lives in one
`@Configuration`, a `@DataJpaTest` that only wants `EntityRepository` still
processes the *entire* `BeanConfig`, including `@Bean` methods that need
beans the slice never loads (e.g. `MeterRegistry`, only present when
Actuator autoconfiguration runs) — and fails context refresh with
`UnsatisfiedDependencyException` even though nothing in that test ever asks
for the service.

**Fix: `@Lazy` on both the bean definition and the injection point that
consumes it — one alone is not enough.**

```java
@Bean
@Lazy   // defers creation until something actually demands it
public EntityService entityService(EntityRepository repo, EntityMapper mapper, MeterRegistry meterRegistry) {
    return new EntityServiceImpl(repo, mapper, meterRegistry);
}

@Bean
public EntityController entityController(@Lazy EntityService service) {  // <-- @Lazy here too
    return new EntityController(service);
}
```

Why both are required: `@Lazy` on the bean *definition* only means "don't
create me until demanded" — it does **not** make every consumer receive a
deferred proxy automatically. If `entityController`'s factory method isn't
itself lazy, its parameter resolution during eager context refresh *is*
exactly such a demand, and immediately forces `entityService(...)` to run,
defeating the point. Marking the **parameter** `@Lazy` makes Spring inject
a lightweight JDK proxy (the target type here is always an interface, so no
CGLIB needed) instead of resolving eagerly — the proxy only touches the
real bean (and its `MeterRegistry` dependency) on first actual method call,
which never happens in a slice test that doesn't use it.

## Verify, don't claim

1. `mvn clean verify` — pay attention to *which* test class fails if
   anything does; a `@DataJpaTest`/`@WebMvcTest` failing with "no
   qualifying bean" for something unrelated to what it tests is the signature
   of §4's pitfall, not a real wiring bug.
2. Run the full app (`mvn spring-boot:run` or the Docker image) and hit a
   real endpoint through the controller, a real 404 through the exception
   handler, and confirm the access-log filter still logs — a green build
   proves the context loads, not that MVC routing and advice actually work.
3. If a class was corrupted mid-build by an IDE's background compiler
   (see the Windows/VS Code note in `create-microservice`), a
   `ClassNotFoundException`/`NoClassDefFoundError` for a *bare simple class
   name with no package* during context refresh is that bug, not a real
   dependency problem — kill the stray process and rebuild clean before
   trusting any other diagnosis.
