# Swagger and OpenAPI Documentation Instructions

## Objective

Every REST API in this project must expose complete, accurate, and maintainable API documentation using OpenAPI and Swagger UI.

These instructions must be followed together with:

- `CRUD_INSTRUCTIONS.md`
- `ENGLISH_PROJECT_INSTRUCTIONS.md`
- `CUCUMBER_API_TESTING_INSTRUCTIONS.md`

All API documentation, descriptions, summaries, examples, schema descriptions, validation descriptions, and error documentation must be written in English.

---

## Required Technology

Use:

- OpenAPI 3
- Swagger UI
- Springdoc OpenAPI for Spring Boot projects

Use a Springdoc OpenAPI version compatible with the Spring Boot version used by the project.

Do not use obsolete Swagger/Springfox dependencies when Springdoc OpenAPI is appropriate.

---

## Required Documentation

Every REST endpoint must be documented.

For a standard CRUD resource, document at minimum:

```text
GET    /api/resources
GET    /api/resources/{id}
POST   /api/resources
PUT    /api/resources/{id}
DELETE /api/resources/{id}
```

If PATCH, search, pagination, filtering, sorting, upload, download, or custom actions exist, they must also be documented.

---

## OpenAPI Configuration

Create a dedicated OpenAPI configuration class when useful.

Recommended location:

```text
src/main/java/com/example/project/config/OpenApiConfig.java
```

The OpenAPI definition must include:

- API title
- API description
- API version
- Contact information when available
- License information when applicable
- Server information when useful

Example:

```java
@Configuration
public class OpenApiConfig {

    @Bean
    public OpenAPI customOpenAPI() {
        return new OpenAPI()
                .info(new Info()
                        .title("Results API")
                        .version("1.0.0")
                        .description("REST API for managing match results"));
    }
}
```

Do not hardcode environment-specific production URLs unless explicitly requested.

---

## Controller Documentation

Use OpenAPI annotations where they improve clarity.

Typical annotations include:

```text
@Tag
@Operation
@ApiResponse
@ApiResponses
@Parameter
@RequestBody
@Schema
@ExampleObject
```

Avoid redundant annotations when Springdoc can infer information correctly.

Documentation must add useful business meaning rather than merely repeat method names.

---

## Tagging

Every controller must have a meaningful OpenAPI tag.

Example:

```java
@Tag(
    name = "Results",
    description = "Operations for managing match results"
)
```

---

## Operation Documentation

Every endpoint must have:

- A concise summary.
- A useful description when needed.
- Expected success response.
- Relevant error responses.

Example:

```java
@Operation(
    summary = "Get a result by id",
    description = "Returns the match result associated with the specified identifier."
)
```

---

## Response Documentation

Document every meaningful HTTP status returned by the endpoint.

For CRUD APIs this normally includes, where applicable:

```text
200 OK
201 Created
204 No Content
400 Bad Request
404 Not Found
409 Conflict
422 Unprocessable Entity
500 Internal Server Error
```

Only document status codes that the API can actually return.

Example:

```java
@ApiResponses({
    @ApiResponse(
        responseCode = "200",
        description = "Result found"
    ),
    @ApiResponse(
        responseCode = "404",
        description = "Result not found"
    )
})
```

---

## Error Response Schema

If the project has a standard API error response, document it as an OpenAPI schema.

Example model:

```json
{
  "timestamp": "2026-01-01T12:00:00Z",
  "status": 404,
  "error": "Not Found",
  "message": "Result not found",
  "path": "/api/results/999"
}
```

Every endpoint that can return this error format must reference the same documented schema.

Avoid defining inconsistent error formats endpoint by endpoint.

---

## DTO Documentation

Every request and response DTO must be documented with meaningful schema information.

Use `@Schema` when needed to describe:

- Field purpose
- Example value
- Required state
- Format
- Minimum or maximum values
- String length limits
- Enumerated values
- Read-only or write-only behavior

Example:

```java
@Schema(
    description = "Unique match identifier",
    example = "MATCH-2026-001"
)
private String matchId;
```

---

## Generated ID Documentation

For generated database identifiers:

```java
@Schema(
    description = "Unique identifier generated by the server",
    example = "1",
    accessMode = Schema.AccessMode.READ_ONLY
)
private Long id;
```

Clients should not be instructed to generate server-owned identifiers.

---

## Request Examples

POST, PUT, PATCH, and other endpoints accepting JSON bodies should include realistic request examples where useful.

Example:

```json
{
  "matchId": "MATCH-2026-001",
  "homeTeam": "Real Madrid",
  "awayTeam": "Barcelona",
  "homeScore": 2,
  "awayScore": 1
}
```

Examples must satisfy the documented validation rules unless they are explicitly examples of invalid requests.

---

## Response Examples

Provide realistic success response examples.

Example:

```json
{
  "id": 1,
  "matchId": "MATCH-2026-001",
  "homeTeam": "Real Madrid",
  "awayTeam": "Barcelona",
  "homeScore": 2,
  "awayScore": 1
}
```

Provide error examples for important failure responses when useful.

---

## Validation Documentation

OpenAPI documentation must reflect validation rules implemented in the API.

For example, if a DTO uses:

```java
@NotBlank
@Size(max = 100)
private String homeTeam;
```

the generated OpenAPI schema must communicate that the value is required and has the appropriate maximum length.

Do not document constraints that are not enforced by the implementation.

Do not enforce constraints in code without reflecting them in the API documentation where possible.

---

## Path Parameters

Every path parameter must be documented.

Example:

```java
@Parameter(
    description = "Unique identifier of the result",
    example = "1",
    required = true
)
@PathVariable Long id
```

---

## Query Parameters

Pagination, filtering, search, and sorting parameters must be documented with:

- Purpose
- Type
- Required/optional state
- Default value when applicable
- Allowed values
- Examples

---

## Pagination

If pagination exists, document:

```text
page
size
sort
```

and clearly describe the response format.

Document page numbering rules, default page size, maximum size if applicable, and sorting syntax.

---

## Swagger UI

Swagger UI must be enabled for development/test environments unless security requirements explicitly prevent it.

The project must document the URL used to access Swagger UI.

Typical Springdoc URLs are commonly based on:

```text
/swagger-ui.html
/swagger-ui/index.html
```

The exact active URL must be verified against the project's actual Springdoc configuration.

---

## OpenAPI JSON and YAML

The application must expose its generated OpenAPI specification.

The project must verify the active OpenAPI endpoint, typically based on:

```text
/v3/api-docs
```

When YAML output is supported/configured, document its corresponding endpoint as well.

Do not assume endpoint paths if they have been customized in application configuration.

---

## OpenAPI File Export

After the API is complete, generate or export an OpenAPI specification file when practical.

Preferred locations:

```text
docs/openapi.json
docs/openapi.yaml
```

At least one machine-readable OpenAPI artifact should be available for consumers when the project workflow supports exporting it.

The generated file must match the running API.

---

## Documentation Synchronization

Swagger/OpenAPI documentation must never knowingly contradict the implementation.

Whenever an endpoint changes:

1. Update its OpenAPI documentation.
2. Update DTO schemas.
3. Update request/response examples.
4. Update documented HTTP response codes.
5. Update validation descriptions.
6. Update Cucumber scenarios when behavior changed.
7. Regenerate exported OpenAPI files if the project stores them.
8. Verify Swagger UI after changes.

---

## Cucumber and OpenAPI Consistency

The documented API behavior and the Cucumber tests must agree.

Examples:

- If OpenAPI documents `404`, Cucumber should test the corresponding not-found behavior.
- If a DTO field is required in OpenAPI, validation tests must confirm the API rejects missing values.
- If POST documents `201`, the Cucumber happy-path scenario must verify `201`.
- If DELETE documents `204`, the Cucumber scenario must verify `204`.

When documentation and implementation disagree, fix the inconsistency before considering the task complete.

---

## OpenAPI Validation

After generating the API documentation:

- Start the application.
- Verify that the OpenAPI endpoint responds successfully.
- Verify Swagger UI loads successfully.
- Verify all controllers appear.
- Verify every endpoint appears.
- Verify request schemas.
- Verify response schemas.
- Verify documented status codes.
- Verify examples.
- Verify validation metadata.
- Verify error schemas.

If the build has an OpenAPI validation mechanism available, use it.

---

## Security Documentation

If authentication or authorization is introduced, document it in OpenAPI.

Supported examples may include:

```text
Bearer JWT
OAuth2
API Key
Basic Authentication
```

Define the appropriate security scheme and apply it only to endpoints that require it.

Never include real passwords, API keys, access tokens, or secrets in OpenAPI examples.

---

## Production Safety

Swagger UI exposure in production must follow the project's security policy.

If production Swagger UI should be disabled:

- Keep OpenAPI generation available where required.
- Configure environment-specific access.
- Document how the behavior differs between development, test, and production.

Do not expose internal or sensitive endpoints unintentionally.

---

## Documentation Test

After implementation, verify at least:

```text
OpenAPI specification endpoint -> HTTP 200
Swagger UI -> accessible in the intended environment
```

Where practical, add an automated smoke test confirming that the OpenAPI specification endpoint is available.

---

## README Integration

The project README must contain an API Documentation section with:

- How to start the application.
- Swagger UI location.
- OpenAPI specification location.
- How to run Cucumber tests.
- Cucumber HTML report location.

Example:

```text
API Documentation
Swagger UI: http://localhost:8080/swagger-ui/index.html
OpenAPI: http://localhost:8080/v3/api-docs

Testing
Run: mvn test
Cucumber report: target/cucumber-reports/cucumber.html
```

Use the real configured URLs rather than blindly copying these examples.

---

## Final Workflow

After CRUD implementation and Cucumber testing are complete:

1. Review all implemented endpoints.
2. Add Springdoc OpenAPI dependencies if missing.
3. Configure OpenAPI metadata.
4. Document all controllers.
5. Document all operations.
6. Document request DTOs.
7. Document response DTOs.
8. Document validation constraints.
9. Document error responses.
10. Add realistic examples.
11. Start the application.
12. Verify Swagger UI.
13. Verify the generated OpenAPI specification.
14. Run the complete Cucumber test suite.
15. Ensure tests pass.
16. Generate the Cucumber report.
17. Export OpenAPI JSON/YAML when the project workflow requires it.
18. Update README documentation.
19. Fix all inconsistencies before considering the task complete.

---

## Completion Criteria

The API documentation task is complete only when:

- Swagger UI works.
- OpenAPI 3 specification is generated.
- Every endpoint is documented.
- Every relevant HTTP response is documented.
- DTO schemas are documented.
- Validation rules are represented.
- Error responses are represented.
- Useful examples exist.
- Documentation is written entirely in English.
- OpenAPI behavior matches the implementation.
- OpenAPI behavior matches Cucumber tests.
- The application compiles.
- The complete test suite passes.
- The Cucumber HTML report is generated.
- Swagger/OpenAPI access is documented in README.
- No secrets are exposed.

---

## Priority

When used together:

- `CRUD_INSTRUCTIONS.md` defines CRUD architecture and implementation rules.
- `ENGLISH_PROJECT_INSTRUCTIONS.md` defines the English-only convention.
- `CUCUMBER_API_TESTING_INSTRUCTIONS.md` defines API testing and reporting.
- This file defines Swagger and OpenAPI documentation requirements.

All instruction files must be respected before the API is considered complete.
